# Постоянная история помощника

## Хранение и жизненный цикл

Новая таблица assistant_runs в PostgreSQL проекта (127.0.0.1:55432) хранит отдельные запросы к API помощника. Таблица tickets не менялась, база инструкций pgvector55433 остаётся отдельно. Учебные аварии по-прежнему читаются из JSON.

У каждой записи есть UUID, тип запроса, status, request_data/response_data JSONB, публичное сообщение ошибки, время начала и завершения. Типы: diagnostics, outage (прямое чтение), outage_assistant (выбор инструмента моделью), ticket_draft.

backend/history.py оборачивает вызов:

1. INSERTstatus=started и COMMIT до выполнения. Другой запрос уже может увидеть запись.
2. Выполнение функции/модели. Транзакция БД на это время закрыта.
3. Проверка результата через соответствующую Pydantic response-схему. В журнал попадает именно публичный ответ, без лишних полей.
4. UPDATEstatus=completed, результат и время завершения, затем COMMIT. Только после этого возвращается успешный ответ API.

При ошибке модели/инструмента записывается failed и безопасное публичное сообщение, затем API возвращает исходную ошибку. Сырые исключения, параметры подключения, системные промпты и скрытые рассуждения не собираются. У завершённого модельного вызова аварий сохраняются tool_name/tool_result; у прямого инструмента — его тип и фактический результат. Это журнал запросов и результатов, а не полная пошаговая трасса всех внутренних вызовов.

Если история недоступна до начала, операция не запускается и API отдаёт503. Если финальныйCOMMIT не подтверждён, успешныйHTTP не возвращается; это не доказывает отсутствия записи после сетевой неопределённости. Если не удалось записать исходную ошибку, она не подменяется ошибкой журнала. Запись может остаться started.

Поэтому UI показывает started как **«Итог не записан»**, с пояснением, что выполнение могло прерваться. Это не утверждение, что запрос продолжает исполняться. Автоматического возобновления и повторного запуска операций нет. Максимум одного разрешённого инструмента на запрос сохраняется.

## Что видно в интерфейсе

Ссылка «История» в шапке ведёт к блоку под рабочим пространством. Видны последние20запросов, новые первыми. Раскройте запись, чтобы прочитать вопрос/описание, ответ, выполненную проверку аварий либо сообщение ошибки.

GET /api/history?limit=20 читает журнал. limit ограничен1..50. Само чтение истории не создаёт новые записи. После ответов API помощника браузер обновляет журнал через локальное событие; ручная кнопка полезна для запросов из /docs или после отменённого ожидания. При ошибке загрузки видна ошибка; ранее загруженные записи не выдаются за обновлённые данные.

Это общая локальная учебная история без авторизации и отдельных диалогов. Сохранённые записи доступны для просмотра. Модель получает данные текущего запроса; автоматическая подстановка прошлых сообщений пока не реализована.

Черновики теперь тоже остаются в истории генерации, но создание заявки по-прежнему требует отдельного нажатия «Создать заявку». saved=false в ответе черновика означает **заявка не создана**. Предпросмотр и несохранённые правки формы после обновления страницы сбрасываются, исходный ответ модели можно прочитать в журнале. Нажатия «Применить»/«Отменить» и правки предпросмотра отдельными событиями пока не записываются.

Запрос с невалидными данными, отклонённый422 до маршрута, не запускает журналирование. Внутренние функции и проверочныеCLI не логируются автоматически: обёртка находится на четырёх API-маршрутах. Создание заявки остаётся отдельным бизнес-действием в таблицеtickets.

## Подготовка базы

После запуска локальной базы, перед первым использованием обновлённого API:

```powershell
.\.venv\Scripts\python.exe scripts/local_db.py
.\.venv\Scripts\python.exe scripts/init_history.py
.\start.ps1
```

init_history.py выполняет только backend/history.sql: CREATE TABLE/INDEX IF NOT EXISTS. Повторный запуск не удаляет данные. Он проверен дважды. На время проверок не изменялись jobpilot8000 и общий PostgreSQL5432.
