# Черновик → проверка → явное сохранение

## Поведение

POST /api/assistant/ticket-draft принимает только description. Модель через JSON schema предлагает subject/description или выбирает clarify. Имя, номер, статус, saved и команды записи модель задавать не может: лишние поля отклоняются. Результат API всегда saved=false (заявка не создана). Для известной неопределённой фразы «ничего не работает» используется уже существующий rag.needs_subject: уточнение без вызова модели, model=null. Теперь API-запрос и предложенный текст сохраняются отдельно в [истории](history.md).

Новый backend/ticket_draft.py не вызывает БД. В ai.prepare_ticket_draft нет tools. Используются общий HTTP-парсер, общий pipeline-слот и model-слот; таймаут модели120с, клиента130с. Некорректный/незавершённый ответ →502, недоступность модели →503, таймаут →504. Длинные описания могут потребовать сокращения, если модель не завершает ответ в пределах лимита генерации.

UI:

1. Пользователь вводит исходное описание и нажимает «Подготовить черновик».
2. Появляется отдельный редактируемый предпросмотр. Основная форма не меняется.
3. «Отменить черновик» сохраняет исходные поля. Отмена доступна и во время ожидания.
4. «Использовать в форме» переносит проверенные тему/описание, сохраняя текущее имя пользователя. Это ещё не запись.
5. Пользователь проверяет обычные поля и отдельно нажимает «Создать заявку». Только существующий POST /api/tickets сохраняет данные.

Во время ожидания/предпросмотра кнопка создания заблокирована, а handleSubmit игнорирует submit, включая Enter. Пустые поля предпросмотра не применяются. Смена исходного описания отменяет ожидание и сбрасывает черновик; запоздавший результат не подменяет текст. При сетевой ошибке исходные поля сохраняются. Отмена клиентского ожидания не гарантирует остановку уже начатой генерации на сервере.

У TicketDraftAssistant и Diagnostics разные префиксы ключей React: draft: и diagnostics:. Одинаковые ключи соседей при изменении описания приводили к дублированию блока; ошибка воспроизведена браузерным сценарием и исправлена.

## Что означает подтверждение

Здесь реализован процесс draft → human review → manual submit. Агенту не зарегистрирован write-инструмент. Старый ручной POST /api/tickets по-прежнему принимает поля заявки; серверный протокол токена подтверждения и автономное создание агентом не реализованы. Не представлять текущий интерфейс как серверную защиту от произвольного HTTP-клиента.

Проверка Pydantic гарантирует структуру и длины, а не фактическую точность перефразирования. Человек должен сравнить черновик с исходными симптомами и выполненными действиями. Модель не получает результат ранее выполненной проверки аварий автоматически: у этого вызова источником является только введённое описание.
