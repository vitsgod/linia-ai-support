# Модель выбирает разрешённый инструмент

## Как это работает

Новый POST /api/assistant/outage получает вопрос и выбранный учебный район. Модель видит описание функции `check_outage_status` и схему её аргументов, а не исходный Python-код. Для запроса аварии она может вернуть native `tool_calls` Ollama:

```json
{"function":{"name":"check_outage_status","arguments":{"area_code":"demo-north"}}}
```

backend/outage_assistant.py проверяет, что запрос ровно один, имя разрешено, аргументы соответствуют строгой Pydantic-схеме и район совпадает с выбранным в интерфейсе. Только затем Python вызывает функцию. Не используются eval, произвольный getattr, команды ОС, URL модели или доступ ко всем функциям приложения.

Схема, отправляемая модели, разрешает только выбранный код района. Эта подсказка не заменяет серверную проверку. Подмена района, лишние аргументы, несколько вызовов и неизвестное имя дают502 **до выполнения**. В частности, create_ticket не является разрешённым инструментом.

Функция читает тот же data/demo_outages.json. Сервер собирает итоговый текст из area_name/message фактического OutageResult и возвращает mode=tool_result, tool_name и tool_result. Свободный текст модели без tool_calls не может подтверждать аварию: приложение выдаёт фиксированное уточнение. Район не выбран — уточнение до обращения к Ollama.

Это один модельный выбор и максимум одно read-only действие. На этом шаге результата функции **не отправляем вторым запросом обратно модели**: роль tool и свободный модельный пересказ не нужны для показа статуса из структурированных данных. Не заявлять реализацию полного агентного цикла. Сохранение истории вызовов, нескольких шагов и подготовка заявки остаются отдельными этапами.

Протокол проверен по [официальной документации Ollama](https://docs.ollama.com/capabilities/tool-calling). У установленной qwen3:4b /api/show содержит capability tools; реальный /api/chat возвращает tool_calls. Наличие tools в metadata само по себе не использовалось как доказательство успешного вызова.

## Интерфейс и API

1. В описании проблемы напишите «Проверь, есть ли авария в выбранном районе».
2. Выберите учебный район.
3. Нажмите **«Проверить через помощника»**. Прямая кнопка «Проверить аварии» остаётся для сравнения.

Вопрос берётся из описания, максимум1000символов для этого вызова. Имя и тема не требуются. После смены описания или района результат помощника очищается и ожидание старого запроса отменяется. Уже начатая серверная генерация при этом может продолжаться; новые запросы могут получить503«занято». Один общий pipeline-слот с RAG и один model-слот исключают одновременную работу этих маршрутов внутри процесса.

Модель имеет таймаут120с, клиент130с; слишком большой/повреждённый/незавершённый ответ отклоняется. Недоступный источник аварий возвращает503. HTTP200 означает завершённый ответ API, а mode различает реальное выполнение инструмента и просьбу уточнить. Ошибки не превращаются в статус «аварий нет».

API остаётся на8001, интерфейс5173. JSON аварий не перенесён в БД; обсуждение реальной архитектуры не меняло текущий учебный план. Заявки не создаются и не изменяются этим маршрутом. Позднее добавлен постоянный журнал API-запросов и результатов: [history.md](history.md). Полного многошагового цикла по-прежнему нет.
