# Ответы с поиском по инструкциям

## Что теперь происходит

React отправляет описание в POST /api/diagnostics. backend/rag.py:

1. Известные неопределённые фразы вроде «ничего не работает» сразу получают уточнение. Это узкое правило, не универсальное понимание смысла.
2. embed_query вычисляет вектор только вопроса; PostgreSQL55433 возвращает top3. Никакой повторной индексации документов.
3. Кандидаты с cosine similarity ниже0.55 отбрасываются. При отсутствии кандидатов ответ-уточнение формирует Python без генерации, model=null.
4. ai.py отправляет Qwen3 в JSON вопрос и **текст** оставшихся фрагментов с id. Модель не читает PostgreSQL и Markdown сама; веса модели не изменяются.
5. Модель возвращает JSON mode=answer/clarify, answer и source_ids. Используется JSON schema формата Ollama: https://docs.ollama.com/api/chat . Правила идут в system, вопрос и материалы — в user как данные.
6. Pydantic проверяет формат; Python проверяет id по переданным материалам. Чужие/повторныеid, ответ без источника, некорректный JSON →502. При clarify приложение выдаёт фиксированное уточнение, без советов и источников.
7. React показывает ответ, раскрываемые фрагменты и ссылки на полные учебные инструкции. Текст — обычный React text, не HTML модели. Ссылки строит сервер; разрешены существующие Markdown изknowledge/. Клиент также отклоняет внешние/опасные URL.

Источники показывают фрагменты, на которые сослалась модель. Это позволяет проверить утверждения, но не доказывает автоматически, что каждое утверждение ими обосновано. Раскрытый текст — сохранённый фрагмент изБД, полная инструкция открывается в текущей версии Markdown; после её изменения нужна повторная индексация.

## Запуск

Порт8000 занят другим проектом jobpilot. Его не останавливали. Этот проект теперь использует8001, прокси Vite и README обновлены.

Docker Desktop и Ollama должны работать. Из корня проекта:

```powershell
.\.venv\Scripts\python.exe scripts/local_db.py
.\.venv\Scripts\python.exe scripts/local_vector_db.py
# При первой подготовке или изменении инструкций:
.\.venv\Scripts\python.exe scripts/index_knowledge.py
.\.venv\Scripts\python.exe scripts/prepare_rag.py
.\start.ps1
# Во втором терминале:
.\start-frontend.ps1
```

Интерфейс http://127.0.0.1:5173/ ; API http://127.0.0.1:8001/docs . prepare_rag.py создаёт knowledge_reader: NOSUPERUSER, без создания ролей/баз; CONNECT, USAGEpublic и SELECTknowledge_chunks. Пароль в игнорируемом .local/vector-reader.env. API подключается этой ролью, дополнительно с read_only=on; bootstrap остаётся дляиндексации. Ошибки поиска не превращаются в свободную генерацию и не показывают параметры подключения.

Один запрос допускается на весь pipeline. Embedding и генерация имеют отдельные таймауты120с, клиент ждёт250с. Изменение описания отменяет ожидание и очищает результат. Разрыв клиентского ожидания не гарантирует остановку уже начатой генерации Ollama. Диагностика не создаёт заявку и не сохраняет ответы.

## Что ещё требует работы

Ручная проверка выявила повтор проверки кабелей в ответе, хотя пользователь написал «кабели проверены». На следующем учебном шаге добавлен узкий контроль повторных действий после генерации: [rag-quality.md](rag-quality.md). Корректный JSON и существующие источники всё равно не обеспечивают соблюдение всех фактов. Не объявлять RAG безошибочным.

Порог0.55 выбран для текущей маленькой базы/QwenEmbedding, его нельзя считать универсальным. Разные формулировки могут проходить или отсеиваться неверно; система не гарантирует устойчивость к любым инструкциям в пользовательском тексте.
