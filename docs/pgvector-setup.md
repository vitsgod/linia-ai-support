Из корня проекта, при работающих Docker Desktop и Ollama:

```powershell
.\.venv\Scripts\python.exe scripts/local_vector_db.py
.\.venv\Scripts\python.exe scripts/index_knowledge.py
.\.venv\Scripts\python.exe scripts/search_vector_knowledge.py --query "На телефоне интернет есть, а на ноутбуке нет"
```

Первую индексацию нужно выполнить один раз. После изменения Markdown повторить index_knowledge.py. Он пересчитывает фрагменты, а затем атомарно заменяет только knowledge_chunks: ошибка записи откатывает замену. При обычном поиске документы не пересчитываются, embedding-модель получает только вопрос. В таблице сохраняются id, текст, источник, модель и vector(1024). Модель при поиске должна совпадать с моделью документов. При замене весов под тем же именем также нужна повторная индексация.

SQL в backend/vector_store.py использует параметризованные значения:

```sql
SELECT id, source, text,
       1 - (embedding <=> %s::vector) AS score
FROM knowledge_chunks
WHERE model = %s
ORDER BY embedding <=> %s::vector, id
LIMIT %s;
```

`<=>` — cosine distance, меньше означает ближе; `1 - distance` — similarity, больше означает ближе. Это не вероятность правильности. На12строках используется точный перебор без приближённого HNSW-индекса. Слово «индексация» здесь означает подготовку поискового набора документов.

Пароль генерируется в .local/vector.env, игнорируется Git. Файл сохранять вместе с Docker volume: при его утрате скрипт не меняет пароль существующей базы. Именованный volume knowledge-data переживает остановку и перезапуск контейнера. Не выполнять down -v, если данные нужны. Для остановки без удаления: local_vector_db.py --stop.

Учебные CLI-скрипты подключаются локальной bootstrap-ролью, которая может создать расширение. Перед подключением поиска к веб-API следует выделить роль с минимальными правами чтения, а bootstrap оставить только для подготовки базы. Это не конфигурация публичного сервиса.
